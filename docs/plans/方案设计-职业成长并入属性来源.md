# 职业属性只是属性：删除 `natural` 通道

> 修正上一版分析的方向。上一版把"职业成长"当成需要单独表达的来源，并设计了 `planners-job` 来源与 `job.*` 根——这是错的。
> 本质：**只有属性这一条路**。"职业"是业务上的叫法，职业提供的数值和装备、Buff、技能、加点一样，都是属性；引擎不需要、也不应该有第二条读取通道。
> 状态：已按方式 A 实施（见第七节）。

---

## 一、结论

1. 删除 `natural.*` 查询根，不保留别名，不新增 `job.*`。
2. 删除 `ActionAttributeAccess.NaturalReader` 注入槽与 FightCore 的 `installNatural`/`readNatural`。
3. 不按业务语义拆属性来源：`planners-proxy` 继续作为 Planners 的属性来源写入，来源名只是技术标识，不是业务概念。
4. 属性只有一个读源：`AttributeDriver`（`attr.*`）。所有消费方（技能公式、UI、第三方）都读这一条路。

---

## 二、为什么不需要 `natural`

- 职业属性已经是属性：Planners 算出后经 `AttributeProxy.sync` → `AttributeDriver.setValues` 写入，和装备、Buff 走同一个容器。
- 因此"职业自然成长"不是一个引擎概念，只是**同一份属性里由职业配置贡献的那部分**。为了读它再开一个查询根，等于给属性系统造第二条读路径。
- 一旦有两条路径，就会出现：驱动缺失时 `attr.*` 缺失而 `natural.*` 有值；刷新时机不同导致同一属性两个数；职业公式改一次要同步两处实现。
- 名字也不是问题：业务想叫"职业属性""自然成长"都可以，但它落地就是属性，读取只有一条路。

---

## 三、删除后受影响的业务表达

`natural` 之所以被用，是因为伤害/治疗公式想表达"只对超出职业基础的部分加成"。删除通道后，这个诉求有三种落地方式：

| 方式 | 做法 | 评价 |
| --- | --- | --- |
| **A. 公式直接用总属性** | `fc.damage.skill` 的 `main=<attr.strength>`，去掉 `natural` 参数与减法 | 最简单、最符合"只有属性"；但低等级玩家也会吃到主属性加成，数值需要策划重新确认 |
| **B. 技能配置显式给数** | 技能 `variables` 里写 `naturalStrength: "..."`，公式传该变量 | 现状 `sage_prayer_minor_bolt` 已经在用；缺点是业务公式重复维护一份 |
| C. 保留减法但由属性层提供"差值" | 属性层新增聚合/来源概念 | 与本次结论冲突，不做 |

推荐 A；如果策划坚持"只对额外部分加成"，用 B 并在技能里显式声明，但不要把它做成引擎概念。

## 五、风险

| 风险 | 说明 |
| --- | --- |
| 数值变化 | 方式 A 会让主属性项从"无加成"变成"按总属性加成"，治疗量也变化；必须由策划确认目标区间后回归 |
| 参数移除的兼容性 | `fc.damage.skill` / `swept` 移除 `natural` 后，旧配置必须同步删除该参数，否则加载期报未知参数（与现有"显式配置、拒绝旧字段"一致） |
| 缺少"额外加成"表达 | 如果策划坚持该规则，只能用方式 B 显式写；不要回流成引擎能力 |
| 第三方读取 | 只有 `attr.*` 后，UI 只能看到汇总值；如确需分来源展示，那是属性面板的展示需求，不应反向影响技能公式 |

验收建议：`attr.<主属性>` 与职业公式值一致（同一等级）、装备/Buff/节点变化只影响 `attr.*`；技能伤害与治疗按新公式回归；`natural.*` 在配置与文档中零残留。
