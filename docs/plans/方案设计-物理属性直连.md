# 物理属性直连改造方案

> 目标：删除 Planners 内置的"逻辑属性 → 物理属性"转换层，属性来源直接输出物理属性 ID，一次推入 `AttributeDriver`。
> 后续：本文中 `natural.*` 只做键改名的约定已被推翻，该查询根随后整体删除，见[职业属性只是属性](方案设计-职业成长并入属性来源.md)。
> 前置结论：服务端现行 `settings.attribute.registry` 共 14 项，系数全部为 `1.0`，转换层实际只做了一个改名动作。
> 影响仓库：`planners-v2`（代码 + 默认资源 + 单测 + 文档）、`server-main`（业务配置 + Nova 用例 + Skill 文档）。

---

## 一、结论

1. 删除 `settings.attribute.registry`、`AttributeRegistryEntry`、`AttributeConversion`、`AttributeProxy` 的分流/转换/合并三段逻辑。
2. `AttributeSource.getAttributes()` 返回的键即物理属性 ID（本服为 FightCore 属性 ID），`AttributeProxy` 只做同键累加，然后 `AttributeDriver.setValues(entity, "planners-proxy", map, -1)`。
3. 服务端配置按 `1.0` 系数逐键改名，数值结果不变；不保留旧键别名，不做兼容读取。
4. `AttributeProvider` 的线程、代际、重载、在线补刷协议完全不动。

---

## 二、现状链路与问题

### 2.1 现行链路

```
AttributeSource（hook.attributes / 技能树节点）
   → AttributeProxy.sync 按 registry 分流：命中 registry 的当"逻辑属性"，其余当"物理直通"
   → AttributeConversion.convert 按 YAML 系数换算
   → 合并
   → AttributeDriver.setValues(entity, "planners-proxy", map, -1)
```

代码位置：`core/attribute/AttributeProxy.kt`（分流/合并）、`core/attribute/AttributeConversion.kt`（换算）、`Planners.kt:108-120`（registry 配置节点）、`api/attribute/AttributeRegistryEntry.kt`（数据类）。

### 2.2 服务端现行 registry 实际内容

`server-main/plugins/Planners/config.yml:166-223`，14 项，系数全为 `1.0`：

| 配置键 | 物理属性 | 系数 |
| --- | --- | --- |
| `STR` | `strength` | 1.0 |
| `AGI` | `agility` | 1.0 |
| `INT` | `intelligence` | 1.0 |
| `END` | `endurance` | 1.0 |
| `FAITH` | `faith` | 1.0 |
| `SPI` | `spirit` | 1.0 |
| `HP` | `health` | 1.0 |
| `SP` | `stamina` | 1.0 |
| `MP` | `mana` | 1.0 |
| `HP_REGEN` | `health-regen` | 1.0 |
| `SP_REGEN` | `stamina-regen` | 1.0 |
| `MP_REGEN` | `mana-regen` | 1.0 |
| `DEF` | `defense` | 1.0 |
| `TENACITY` | `tenacity` | 1.0 |

即：这一层没有提供倍率、上限、条件或聚合能力，只是把 FightCore 已有的 ID 换成一个自造的短名。

### 2.3 这层带来的实际问题

1. **两套键并存，同一动作里混用。** 技能写 `main=<attr.strength>`（物理键），却在同一个参数里写 `natural=<natural.STR>`（逻辑键），配置人员必须同时记住两套词表。
2. **写错的键不会被加载期发现。** 逻辑键写错 → 静默当作物理键直通；物理键写错 → 进入 `FightCorePlannersAttributeDriver.setValues` 的 `AttributeManager.requireAttributeInstance` 才抛异常，而这次抛异常发生在 `AttributeProvider` 的刷新任务里，整组 `planners-proxy` 全部不写入。一次笔误等于该玩家所有职业属性一起失效，只剩一行堆栈。
3. **已经存在的键错误实例。**
   - `server-main/plugins/Planners/skill/zombie_slayer.yml:39` 写 `attr.ATK`，FightCore 无此属性（应为 `attr.damage`）。
   - `planners-v2/src/main/resources/skill/example0.yml:27` 用显示名 `"攻击力"` 当属性键；`skill/passive_rage.yml`、`skill/passive_toughness.yml` 用 `ATK`/`DEF` 当物理键。
4. **占位符白名单依赖 registry。** `module/compat/placeholder/PlaceholderLiteral.kt:548-557` 先查 registry 再取值，registry 一改就恒返回空字符串。
5. **文档与代码双份维护。** 逻辑键词表在 `config.yml`、技能文档、Skill 文档、Nova 用例之间重复维护。

## 三、目标链路

```
AttributeSource（hook.attributes / 技能树节点 / 后续模块来源）
   → AttributeProxy.collect：按物理 ID 累加
   → AttributeDriver.setValues(entity, "planners-proxy", map, -1)
```

### 3.1 键约定

- 属性键就是**当前驱动所属属性系统的物理 ID**，本服为 FightCore：`strength`、`agility`、`intelligence`、`endurance`、`spirit`、`faith`、`health`、`stamina`、`mana`、`health-regen`、`stamina-regen`、`mana-regen`、`defense`、`tenacity`、`damage`、`crit`、`power-strike`、`hit-chance` 等。
- 一律 kebab-case 小写，与 FightCore `settings.attribute.entry.registry` 中的 ID 完全一致。
- Planners 不再保存任何属性键表；键是否合法由驱动判定，Planners 不做加载期校验。
- 代价：属性配置与具体属性插件绑定，换驱动需要改配置。这是删除转换层的直接取舍，接受。

### 3.2 行为约定（不变的部分）

- 来源优先级 `PRIORITY_*`、同键累加、按来源 ID 整组替换、空输出移除来源：不变。
- 主线程调度、异步入参复制、代际失效、重载期间拒绝写入、离线/换档案丢弃：不变（`AttributeProvider` 不动）。
- 文本驱动仍走 `AttributeProxy.createTokens`（`id: +值`，普通十进制、不取整、负值单一负号）：不变。
- 最终资源容量取整仍由资源系统负责：不变。

`AttributeProxy` 改造后的形状：

```kotlin
object AttributeProxy {

    fun register(source: AttributeSource)
    fun unregister(source: AttributeSource)

    /** 汇总所有来源的物理属性，同键累加。 */
    fun collect(entity: LivingEntity): Map<String, Double>

    /** 重算并整组推送到驱动。 */
    fun sync(entity: LivingEntity) {
        val physical = collect(entity)
        AttributeDriver.setValues(entity, "planners-proxy", physical, -1)
    }

    internal fun createTokens(physical: Map<String, Double>): List<String>
}
```

## 八、已确认范围

1. `%planners_attribute:<id>%` 占位符**整体删除**，不再提供属性读取占位符。
2. **不新增**加载期键校验（不给 `AttributeDriver` 加 `isKnownAttribute`，不引入跨仓库 API 变更）；键错误由驱动在首次推送时明确报错，靠 §7.4 的一次性扫描在迁移阶段兜住。
3. `natural.*` **只做键改名**，不修读取语义：`FightCoreQueryBridge.readNatural` 仍返回驱动汇总值，`attr.x - natural.x` 恒为 0 的既有缺陷保留，另行处理。
